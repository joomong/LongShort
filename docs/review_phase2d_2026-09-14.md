# Phase 2d 독립 팀 리뷰 — 2026-09-14

검토 기준은 HEAD `2e77af1` 위의 현재 미커밋 작업 트리와 `data/events/events.parquet`이다. 사용자 요청은 리뷰와 추가 문제 탐색이며 제품 코드, 원천 DB/캐시를 수정하거나 커밋하지 않았다. 이 문서만 리뷰 산출물로 추가했다.

root는 실제 이벤트의 HTTP 재현, engine_audit는 생성기의 환산/폴백, build_validation은 로더 가드, frontend_refactor는 검증 범위와 실패 판정을 독립 검토했다.

## 확인된 개선

캐시 앵커 수식은 올바르다. `k_t = 대상 as-traded 가격 / 대상 캐시 가격`, `k_s = 승계사 as-traded 가격 / 승계사 캐시 가격`일 때 `cashCache = cash/k_t`, `ratioCache = ratio*k_s/k_t`이다. 단순히 현재 DB 분할 배수를 캐시 가격에 곱하는 방법과 구분된다.

- 엔진 테스트 48개, 로더 테스트 21개, 독립 원장 self-check 289개를 이번 리뷰에서 재실행해 통과했다.
- 원본 캐시와 실제 생성 이벤트를 사용하는 임시 서버에서 NVLS(2012-06-05) `+0.0394900198`, GOOG(2015-10-06) `+0.0061889358`을 확인했다. 각각 `computedSettlementReturns=1`, guard checks=1이다.
- cash-only의 비단위 대상 배율도 별도로 확인했다. `27069124`, cash=3, cashCache=150000, target cache mark=148000, k_t=0.00002: 2016-02-19 실제 HTTP 수익 `+0.0135135135`, 계산 오차 0이다. 이 경우 현재 가드는 checks=0/skipped=0이다.
- 저장된 전기간 30개 결과가 실제로 성공하고 수수료 항등식 잔차가 작은 것과, 검증 도구 자체가 실패를 정확히 거절하는지는 별개로 검토했다.

## R1 — P1: 혼합 딜의 주식 다리 유실, 실제 엔진 손익 오류

생성기 `build_events.py:1079-1081`에서 승계사 가격/배율 환산이 실패하면 `successorRatioCache`는 NaN이 되지만 `cashPerShareCache`는 남는다. 엔진 `simulator.cpp:209-235`는 유한 ratio 여부로 주식 다리를 판정하므로 이를 현금 전용 거래로 바꾸고, 현금만의 계산 R을 파일 R보다 우선한다.

실제 6,413개 이벤트에서 `cashPerShareCache` 유한 + 원 `successorRatio` 유한 + `successorRatioCache` NaN인 행은 **32개**다. 별도 원본 캐시/이벤트 HTTP 재현:

| 항목 | 값 |
|---|---|
| 종목 | 12678069, IWA / Windstream Iowa Communications |
| 매수·정산일 | 2010-05-28 진입, 2010-06-01 정산 |
| 입력 | 현금 7.9 + 원 주식 교환비율 0.804, 캐시 mark 약 16.66 |
| 파일 R | −0.0108835542 |
| 현재 엔진 | 현금만 `7.9/16.66−1` 계산 → **−0.5258103198** |
| 진단 | computedSettlementReturns=1, defaultDelistings=0 |

이는 파일 R이 실제 경제적 정답임을 증명하는 검사는 아니다. 현재 계약이 요구하는 파일 R 폴백 대신 불완전한 현금 다리가 완전 정산으로 사용됨을 입증한다.

추가로 `build_events.py:1101`은 승계사 ID가 없으면 원 주식 비율까지 지운다. 이 경로 후보 11개 중 원문으로 혼합 대가를 확인한 것은 적어도 4개(2665532, 11114106, 241723627, 282449174)이며 위 32개와 겹치지 않는다. 11개 전부를 확정된 혼합 딜로 집계하지 않는다.

권고: 주식 다리의 존재 여부와 그 다리를 환산/평가할 수 있는지를 별도로 유지한다. 불완전한 다리로 전체 대가를 계산하지 않고, 완전한 파일 R 또는 명시한 미평가 정책으로 넘긴다. 최종 Parquet → 로더 → 엔진을 통과하는 회귀가 필요하다.

## R2 — P1: 기간 선택으로 실제 사용 이벤트의 stale 검사 생략

`parquet_reader.cpp:524-528`은 guard 기준일이 메모리 패널 밖이면 검사를 생략한다. 그러나 해당 이벤트가 거래 기간 안에 있어 환산 계수가 사용될 수 있다.

- 동일 파일: guard Jan1 기준값=999, 실제 소스 close=30; 정산 Jan3.
- 거래 Jan2–Jan4, warmup=0: 로드 성공, checks=0/skipped=1.
- 거래 Jan2–Jan4, warmup=1: stale 오류로 거절.

로더까지 실제 재현했으며 이 사례의 PnL까지 실행한 것은 아니다. 검증용 기준 가격은 시뮬레이션의 적재 구간과 독립적으로 원본에서 확인하거나, 실제 사용할 계수를 검증할 수 없을 때 명시적으로 실패해야 한다.

재현: `/tmp/longshort_p2d_loader_review_20260914/results.json` 및 같은 디렉터리의 `probe`, `past_guard_date_no_warmup/config.json`, `past_guard_date_with_warmup/config.json`.

## R3 — P1: 검증 도구의 실패 판정이 부족함

- `run_top500_missing_close.py:353-355`: 실패 횟수를 출력하지만 exit code에는 반영하지 않는다. HTTP 실패 두 건을 주입해 모두 FAIL이어도 exit 0을 재현했다.
- 같은 도구는 수수료 항등식 오차 0.3인 응답도 OK/exit 0으로 처리한다. 계산된 잔차를 실패 조건으로 사용해야 한다.
- `check_missing_data.py:1066-1067`: 원장이 거절할 케이스에서는 관계없는 HTTP 500도 `both reject` PASS로 처리한다. 예상 HTTP 상태와 오류 종류/위치를 확인해야 한다.

제품 응답을 조작한 것이 아니라 도구 함수를 메모리 내 가짜 응답으로 검사한 결과다. 현재 저장된 정상 실행 기록을 무효라고 주장하는 것은 아니다.

재현 결과: `/tmp/longshort_phase2d_coverage_audit/validator_counterexamples/summary.json`.

## R4 — 합성 입력에서 재현된 생성기 경계

다음은 실코드 분기를 합성 자료로 검사한 문제이며 현재 실제 파일에서 발생했다고 단정하지 않는다.

- DB 대상 가격 조회 실패 시 cacheMark를 as-traded lastClose로 대체하고 이를 k_t=1 앵커로 승인한다. 실제 as-traded 50/cache 100/cash 55인 사례에서 DB 행이 있으면 R=+10%, 없으면 잘못된 R=−45%가 생성된다.
- override 경로가 캐시 가격을 lastClose/acquirerClose에 넣어 k_t/k_s=1을 강제한다. 비단위 캐시를 사용하는 새로운 override에서 같은 가격 기준 오류가 재발한다. 현행 4개 override에 이 문제가 발생했다는 증거는 없다.
- non-USD 거절 경로는 candidate R만 NaN으로 만들고 cache 대가를 남길 수 있다. 합성 입력에서 재현했으나 현재 보고서의 실제 해당 행은 0건이다.

재현 코드: `/tmp/phase2d_generator_anchor_audit.py`.

## 기존 한계와 부수 발견

- 대상 측 가드는 아직 없다. 이는 successor 이벤트의 k_t≠1 30개에만 국한되지 않는다. 현금 전용 딜을 포함해 대상 가격 기준이 바뀌는 모든 경우를 고려해야 한다.

- 가드는 기준 시각을 날짜로 내리므로 일중 복수 bar 입력에서는 오거절/오수락이 가능하다. 현재 일봉 범위의 주요 차단 사유는 아니다.
